**Second correctness review pass (2026-08-16)**: ran `/code-review` across everything shipped since the first pass (`9868fa4..HEAD` — Template Marketplace, Phase 7, and the Candy Machine creator flow). The first two attempts (`max` effort, which fans out into several parallel angle-sub-agents) both failed outright on a session usage limit before producing findings; a third attempt at `high` effort (single-pass) completed. Found and fixed 8 real issues, the most important being in the Solana money flow:
- `MintLaunchPage.tsx`'s launch loop awaited `connection.confirmTransaction()` but never checked the resolved `.value.err` — an on-chain program failure (bad guard config, insufficient funds) resolves *without throwing*, so a failed transaction would have been treated as successful and the flow would proceed to record a deployment for a candy machine that was never actually fully created. Now checked and thrown on.
- `candy_machine.record_candy_machine` verified only that the last transaction *signature* succeeded on-chain, never that it actually touched the claimed `candy_machine` address — a caller could pair any successful signature with an arbitrary address and it'd be persisted as verified. `blockchain.py`'s `_get_solana_transaction_status` now also returns the transaction's `account_keys`, checked against the claimed address before persisting.

**Market Intelligence & DeFi Scanner — happy-path tests + response caching, same day.** Both integrations previously had only their validation-error paths tested ("only the validation-error paths are tested, to stay deterministic/network-free" — Phase 7's own note). Also added a short (30s) server-side cache in front of both, so concurrent page loads don't each trigger their own upstream request:
- `market_intelligence.get_top_tokens` caches per-`limit`, matching CoinGecko's own `per_page` param being limit-scoped — a different limit really is a different upstream request.
- `defi_scanner.get_top_protocols` caches the *entire* sorted list once, not per-limit — DeFiLlama's `/protocols` endpoint has no limit param at all; the existing code was already fetching everything and slicing locally, so caching per-limit (the naive copy of the CoinGecko approach) would have refetched the same full list once per distinct limit seen. - Same per-process caveat as the in-memory rate limiter noted elsewhere in this doc: with more than one gunicorn worker, each worker holds its own cache. Unlike the rate limiter this is a pure optimization, not a correctness issue, so it's a safe improvement on its own; a shared cache (Redis) would be needed to fully dedupe across workers.
